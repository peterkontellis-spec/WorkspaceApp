# Isolated browser regression checks

This harness is a local test tool, not a background watcher or a sign-off claim. It never reads the saved preview's database/auth files and does not target port 3100. Browser execution must use a permitted automation route; do not use this runner to bypass a browser-policy denial. The supported CUA browser can inspect the same isolated fixture server without launching Playwright.

## Commands

Use the project's Node/pnpm runtime. First run `pnpm check` so the production build matches the source under review.

| Command               | Result                                                                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm test:e2e:setup` | Creates/migrates an isolated database, creates four fictional accounts, starts a copied app build, checks authenticated snapshots, then stops app/database. Does not launch a browser.                  |
| `pnpm test:e2e:serve` | Starts the same isolated environment and prints its URL/artifact directory for supported manual/CUA inspection. Remains running until Ctrl+C.                                                           |
| `pnpm test:e2e`       | Starts the environment, runs the committed Chromium Playwright suite, then stops its own app/database even after test failure. Requires permitted browser execution and the installed matching browser. |

Development dependency: pinned `@playwright/test`. If authorized for this environment, install its matching Chromium inside this workspace with `PLAYWRIGHT_BROWSERS_PATH="$PWD/.local/playwright-browsers" pnpm exec playwright install chromium`; do not assume a browser binary is already available. There is no hosted CI job, external service or paid runner. Direct `playwright test` without a disposable manifest deliberately fails. No existing server can be reused through a base-URL override.

For `--serve`, fictional credentials are in the run's `fictional-logins.json` (owner/editor/viewer/second editor); never use actual passwords or preview accounts. The environment initially has an empty workspace. Create test boards through the UI or the existing authenticated API. `manifest.json` includes test-only account IDs, session-state paths, loopback URL and the isolated database administration URL for controlled expiry tests. It must remain private.

## Isolation and retained evidence

Every run owns a new `.local/e2e/run-*` directory, an embedded PostgreSQL cluster, application role, secret, attachments directory, copied production build, and ephemeral loopback app/database ports. Environment settings override inherited runtime settings. Setup proves authenticated account identity before starting tests. No migrations, resets, signals, fixture writes, attachments, sessions or build replacement touch the regular preview. Files are private by default; all artifacts remain under ignored `.local/`.

Fixture setup and login use the server's actual auth/work boundaries with generated fictional credentials; they do not require a browser to create or change passwords. Each browser scenario gets isolated contexts for all four people and creates its own uniquely named board/tasks through the authenticated API. Test fixtures are not evidence for the sign-in/invitation/password-recovery UI journeys.

The runner retains its run directory after stopping so evidence can be inspected. Failure artifacts include per-account screenshots, automatically managed Playwright traces, console/dialog-label diagnostics, and an HTML report; layout cases also attach successful viewport screenshots. Traces and session files can contain fictional credentials/data and must not be committed or published. Remove only the specific run directory after its processes have stopped and its evidence is no longer needed. The runner intentionally does not recursively clean arbitrary paths or use the live preview's restart script.

## Coverage and honest limits

The committed suite has 16 scenarios (nine corrective-flow tests and seven existing-foundation tests), one worker, no retries. A failed scenario fails the command after owned cleanup; the runner explicitly preserves the result because the embedded-database dependency otherwise forces a zero exit code on normal event-loop shutdown.

| Scenario                           | Committed browser assertion                                                                                                                                                                           | Complement / remaining gap                                                                                                                                                                                                         |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M3.1 views/date/filter persistence | Same task identity across Table/Kanban/Calendar; leap-day picker/save; status change; search preserved across views/reload; undated placement                                                         | Existing work-view/date/filter unit and DB checks cover broader input validation. Calendar edge/time-zone variants still need targeted additions if changed.                                                                       |
| M3.2 multiuser updates             | Four separate account contexts observe a saved change through ordinary polling                                                                                                                        | No claim about real four-device load, battery or background OS behavior.                                                                                                                                                           |
| M3.2 reconnect and conflicts       | Offline notice; reconnect fetch; stale draft preserved; rejected stale save; explicit discard/reload                                                                                                  | Lower-level tests cover serialized/backoff/disposal mechanics. Uncertain write-response/network failures remain a separate scenario.                                                                                               |
| Role enforcement                   | Viewer has no write controls; direct task mutation fails; saved record unchanged                                                                                                                      | Existing DB tests cover membership removal and role changes. Full browser role-revocation journey remains pending.                                                                                                                 |
| M3.3 notifications                 | Correct recipients; no self-notification; cross-recipient write denied; read state survives reload; deep link opens task activity; a new assignment updates the Home notification bell without reload | Existing DB tests cover pagination, transaction rollback, no-op/duplicate suppression and restart persistence. Notification list refresh/pagination and every changed-field summary are not exhaustively covered by browser tests. |

| Layout and keyboard                | 1440×900 and 390×844; document overflow; visible Save; title-to-status Tab; Escape/focus return; screenshots                                                                                          | Not a visual design/contrast audit. Actual iPhone/software keyboard, 200% zoom, OS reduced motion and complete light/dark checks remain explicit inspection tasks.                                                                 |
| Client errors                      | Unhandled exceptions and unexpected console errors fail; expected offline/auth/conflict transport diagnostics retained                                                                                | Server logs and full diagnostic/security checks remain separate.                                                                                                                                                                   |

The layout test deliberately asserts the agreed block-2 sticky actions and logical field order. It may fail against the pre-correction build; that is an open acceptance gap, not a reason to weaken the assertion. Keep the task link's `data-saved-task` identity and accessible dialog/control names stable where their meaning has not changed.

Additional corrective browser coverage:

- Quick status/priority updates lock competing controls while saving, persist successive changes and move Kanban cards. A synthetic 503 retains the selected value for retry; a real second-user update causes 409, and retry cannot overwrite it.
- Quick assignee selections preserve two successive assignments in the dropdown across separate saves and reload, without opening a task editor.
- Quick date saves can reopen repeatedly; Close calendar dismisses the whole popup and returns focus without changing the saved date.
- Editors can archive a task and its active subtree, Undo, edit after restoration and restore again through the permanent Archived list after reload. Descendants archived earlier remain archived.
- Whole-board archive is owner-only in UI and direct requests; Archived boards navigation supports restoration. Viewer archive writes and quick controls are denied/absent.
- Remote archive turns a dirty editor read-only while retaining its draft; restoration preserves the draft and its original revision, and a stale save cannot silently replace stored content.
- Restoring a child before its archived parent displays the server rejection in the read-only dialog.

Archive browser tests do not yet upload/download attachments around archive, drive every stale board/group/column/attachment race, exercise every historical notification link or validate separate board-level pre-archived descendants. Use the corresponding database tests as complementary evidence, and keep unexecuted browser/device checks explicit. This suite does not validate backups, a NAS deployment or production capacity.
